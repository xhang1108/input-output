# 🧙 Calctopus Development Guide & Black Magic

This document details the internal architecture, hidden logic ("Black Magic"), and specific implementation details that maintain the stability of Calctopus. Read this before refactoring core components.

## 🧠 Core Architecture: The Brain-Body Cycle

Calctopus separates **Calculation** (Brain) from **Rendering** (Body) to ensure high performance and clean logic.

### 1. The Nervous System (`src/nerves/`)
The Body and Brain communicate via specialized hooks called "Nerves".

-   **`useBrain` (Sensory Nerve):** Listens to changes in the graph and triggers the Brain to think.
-   **`useHand` (Motor Nerve):** Manages user interactions like grabbing, copying, pasting, and duplicating nodes.
-   **`useEar` (Sensory Nerve):** Listens for global keyboard shortcuts (e.g., `Ctrl+C`, `Shift+A`) and mouse movements.
-   **`useEye` (Sensory Nerve):** Manages vision and viewport (Focus, Zoom, Pan).
-   **`useMemory` (Hippocampus):** Provides short-term memory (Undo/Redo) capabilities.
-   **`useMouth` (Communication Nerve):** Handles long-term persistence (Auto-save) and file IO (Import/Export).
-   **`useSpeech` (Language Nerve):** Translates the abstract mathematical logic (AST) into human-readable formulas.

### 2. The Cycle of Reactivity
1.  **Change:** User moves a node or types a number.
2.  **Sensation:** `useBrain` hook detects a change in the `nodes` or `edges` array.
3.  **Fingerprinting:** To avoid re-calculating on simple drags, `useBrain` generates a hash of the graph's *logic* (IDs, values, connections) but ignores *positions*.
4.  **Cognition:** If the hash changes, `Brain.ts` runs a **Topological Sort** to determine calculation order.
5.  **Thought:** The Brain produces a `Thoughts` object map: `{ [nodeId]: { value, error, ast } }`.
6.  **Expression:** `Body.tsx` receives the thoughts and updates the React State.

### 3. Forward Calculation, Backward Expression
-   **Values (Brain):** Function calls flow **Forward** (Input -> Math -> Output).
-   **Formulas (Speech):** Formula generation flows **Backward** (Output -> Math -> Input). The `useSpeech` hook recursively traverses the graph backwards to build the Abstract Syntax Tree (AST) string.

## 🔮 Black Magic (Critical Implementation Details)

These are the tricky parts of the codebase that are easy to break if you don't know why they exist.

### 1. AST Hydration (The "Zombie Formula" Fix)
**Problem:** When saving to `localStorage`, the graph state is serialized to JSON. The ASTs (Abstract Syntax Trees) generated by `mathjs` lose their prototype methods (like `.transform()`) and become plain objects ("dehydrated").
**Symptom:** On page reload, the Result node shows `?` because `useSpeech` tries to call `.transform()` on a plain object and fails.
**The Fix (`Body.tsx`):**
We implemented a check during the brain-to-body sync:
```typescript
// Body.tsx
const isDehydrated = node.data.ast && typeof (node.data.ast as any).transform !== 'function';
// If dehydrated, force an update from the fresh Brain calculation
```
**Rule:** *Never assume an AST in `node.data` has methods until it has passed through the Brain at least once in the current session.*

### 2. Custom Edge Logic
**Problem:** React Flow's default edge styling is static, but we want edges to look different based on what they carry (Purple/Dashed for Formulas, Gray/Solid for Values).
**The Fix (`CustomEdge.tsx`):**
We do **not** rely on parsing the Edge ID string (which is brittle). Instead, we use the `source` prop passed by React Flow to look up the actual Source Node and check its data.
```typescript
// CustomEdge.tsx
const sourceNode = getNode(source); // Robust lookup
const isFormula = ... // Logic based on sourceNode data
```

### 3. Ghost Inputs (The "Default" Handle)
**Problem:** The `Brain` matches inputs based on `targetHandle` IDs (e.g., "a", "b"). However, the **Result Node** has a generic input handle with no ID.
**The Fix (`Brain.ts`):**
The engine has a fallback for edges with no `targetHandle`:
```typescript
if (edge.targetHandle) {
    inputValues[edge.targetHandle] = sourceVal;
} else {
    inputValues['default'] = sourceVal; // The generic input slot
}
```
**Rule:** *If a node has only one input, don't rely on it having a specific ID.*

### 4. BigNumber Precision (The "0.1 + 0.2" Fix)
**Problem:** Native JavaScript `Number` is floating-point, leading to errors like `0.1 + 0.2 = 0.30000000000000004`.
**The Fix (`Brain.ts`):**
We configured `mathjs` to use `BigNumber` globally.
- **Inputs:** All parsing uses `math.bignumber()`.
- **Ops:** We use `math.add()`, `math.subtract()`, etc. instead of native operators.
- **Display:** UI components (`NodeOutput`, `NodeMath`) check for `.toFixed()` capability (Duck Typing) to format both primitive Numbers and BigNumbers.

## 💾 Persistence Architecture

-   **Storage:** `localStorage` key `calctopus-graph`.
-   **Mechanism:** `useMouth.ts` handles the serialization.
-   **Auto-Save:** Triggered by `mouth.savor()` in a debounced `useEffect`.
-   **Safety:** We prioritize user intent. Manual "Reset" (`mouth.diet()`) completely wipes storage to fix corrupted states.

## 🏗️ Adding New Nodes

To add a new node type (e.g., `LogicNode`):
1.  **Component:** Create `src/components/nodes/NodeLogic.tsx`.
2.  **Registration:** Add to `nodeTypes` in `Body.tsx`.
3.  **Brain:** Update `createLocalAST` and `think` in `Brain.ts` to handle the new `type` and its logic.
## 🧩 Atomic Design Philosophy (The RISC Metaphor)

This project follows a strict separation between **Atomic Instructions** and **Macro Triggers**, similar to a RISC (Reduced Instruction Set Computer) architecture:

1.  **Organs as Atoms (RISC)**
    -   Modules like `useHand` provide the smallest possible units of action (e.g., `grab`, `paste`, `delete`).
    -   These functions are **pure logic** and state management. They do not care *how* they are triggered.

2.  **Inputs as Macros (Scripts)**
    -   Modules like `useEar` (Keyboard) and `Skin` (UI) act as scripts.
    -   They contain **NO logic**. Their only job is to bind a user event (e.g., `Ctrl+C`) to an organ's instruction (e.g., `hand.copy()`).

**Why?** This decoupling allows us to change the interface (Skin) or controls (Ear) without ever risking breaking the core business logic (Organs).

### Code Structure Guidelines
To maintain this philosophy, `src/nerves/useHand.ts` and `src/utils/graphPhysics.ts` are structured as follows:

### Level 1: Pure Atoms (`src/utils/graphPhysics.ts`)
- **What:** Pure functions with **NO** dependencies on React or application state.
- **Role:** The "Laws of Physics" for the graph.
- **Examples:** `getBoundingBox` (calculates geometry), `generateOffsetNodes` (math for movement), `createNodeObject` (data structure generation).

### Level 2: State Atoms (`src/nerves/useHand.ts`)
- **What:** Internal helper functions that manage state updates.
- **Role:** The "Muscle Memory".
- **Examples:** `_spawnNodes` (standardized way to add nodes), `_removeNodes` (safe deletion of nodes/edges).

### Level 3: Compound Actions (The Hands)
- **What:** Public-facing methods that compose Physics (L1) and State (L2) atoms.
- **Role:** The "Conscious Actions" exposed to the UI.
- **Examples:**
  - `paste()`: Calls L1 `getBoundingBox` -> L1 `generateOffsetNodes` -> L2 `_spawnNodes`.
  - `duplicate()`: Reuses exact same logic chain as `paste()` to ensure consistency.

## 🧹 Clean Debugging Standard

To maintain the architectural integrity of Calctopus, we follow a strict **Cleanup-After-Debug** protocol:

1.  **Experimental Code Removal**: Once the root cause of a bug is identified and a final solution is implemented (e.g., a CSS fix), all intermediate experimental code (e.g., failed state-reset strategies, temporary console logs, or unused debug helpers) **must be removed**.
2.  **Audit the investigation**: Before considering a task complete, audit every line of code added during the search for the fix. If a change does not directly contribute to the final solution or provide mission-critical defense, it is considered "useless code" and should be deleted to prevent technical debt.
3.  **No Dead Hooks**: Ensure that any debug hooks or helper variables (like `window.calctopus`) are stripped from production-ready code.
